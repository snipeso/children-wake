# Possible Paper/Code Differences To Double-Check

1. Power computation wording  
   The manuscript says spectral power was calculated with MATLAB's `pwelch` using 4 s Hanning windows and 50% overlap. In this repo, [`Analysis/Analysis1_ComputePower.m`](/mnt/c/Users/Sophia/Code/children-wake/Analysis/Analysis1_ComputePower.m) calls `cycy.utils.compute_power` from the sibling Matcycle repo. I checked `../Matcycle/+cycy/+utils/compute_power.m`; it does wrap `pwelch` with a Hanning window, 50% overlap, and `nfft = 2^nextpow2(window * fs)`. This looks substantively consistent, but the paper could mention Matcycle as the wrapper actually called by the repo.

2. "Fully automated" artifact removal versus manual helper script  
   The manuscript describes an automated preprocessing and ICA-based artifact removal pipeline, then separately mentions a manual exception for the Dataset2009 cohort of children under 8. This repo does contain a manual ICA scoring helper, [`Preprocessing/Prep4_ManuallyRemoveICA.m`](/mnt/c/Users/Sophia/Code/children-wake/Preprocessing/Prep4_ManuallyRemoveICA.m). However, that script is not wired into the main preprocessing flow and currently contains hard-coded `Providence/Oddball` paths, not an obvious Dataset2009-specific path. That may simply reflect later local reuse of the helper, but it is worth checking against the manuscript wording.

3. Extended Data versus current figure scripts  
   The manuscript implies the shared Extended Data should support figure reproduction. In code, [`Analysis/PolishData.m`](/mnt/c/Users/Sophia/Code/children-wake/Analysis/PolishData.m) exports `ExtendedData_2.mat`, `ExtendedData_4.mat`, and `ExtendedData_6.mat`. But some figure scripts still expect the full cached `ProcessedData.mat`. The clearest mismatch is [`Analysis/Figure2_Specta.m`](/mnt/c/Users/Sophia/Code/children-wake/Analysis/Figure2_Specta.m), which loads `SpectraRedux` and `FrequenciesRedux`; those variables are not exported in `ExtendedData_2.mat`. I added [`Analysis/ExtendedData_Loaders.m`](/mnt/c/Users/Sophia/Code/children-wake/Analysis/ExtendedData_Loaders.m) to document the closest drop-in replacements, but Figure 2 still cannot be reproduced exactly from the current Extended Data files alone.

4. Environment versions are not pinned in code  
   The manuscript says analyses were run in MATLAB 2023b with EEGLAB v2023.1. The code itself does not pin MATLAB versions. [`Analysis/analysisParameters.m`](/mnt/c/Users/Sophia/Code/children-wake/Analysis/analysisParameters.m) references an older network EEGLAB install (`eeglab2022.0`), while this workspace also contains `../External/eeglab2025.1.0`. This is an environment drift issue more than a conceptual mismatch, but it matters for exact reruns.

5. Sample counts and screening claims cannot be re-verified from the repo alone  
   The manuscript reports 163 participants, 58 ADHD participants, and habitual good sleep quality screening. The actual metadata tables used to derive those counts live on the external data drive, not in this repo. I therefore could not verify from code alone whether every count and screening statement in the paper still matches the final metadata files.

6. Dataset-specific path assumptions are stronger than the manuscript suggests  
   The paper reads like a clean, unified pipeline. The code is faithful to the original environment, but it still contains machine-specific path logic and dataset-specific assumptions in [`Preprocessing/prepParameters.m`](/mnt/c/Users/Sophia/Code/children-wake/Preprocessing/prepParameters.m) and [`Analysis/analysisParameters.m`](/mnt/c/Users/Sophia/Code/children-wake/Analysis/analysisParameters.m). That is normal for a working analysis repo, but if the paper describes the code as directly reusable as-is, that would overstate how portable the current scripts are.
